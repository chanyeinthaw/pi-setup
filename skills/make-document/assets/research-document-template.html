01. Executive summary

Gairoushi provisions application and database capacity continuously even though the workload is low during normal periods and sharply concentrated around scheduled examinations. The production ECS service averaged approximately 2.5% CPU and 6.5% memory in July. On 7 June, however, examination traffic reached 2,919 requests in one minute, with a brief peak of 510 HTTP requests in one second.

The proposed model separates the low baseline from known peaks:

Database

PlanetScale Vitess

PS-20 normally; resize to PS-160 before examination windows. Billing is prorated by time at each size.

Application

AWS Lambda + Bref

Serve Laravel dynamically through Lambda. Move static files to S3 and CloudFront; jobs to SQS-triggered Lambda.

Session & cache

Upstash Redis

Use separate Redis databases for sessions and cache. Keep Lambda outside the VPC where practical.

Recommendation: approve a non-production prototype. Do not decommission ECS or Aurora until the complete examination workflow passes correctness, latency, failure, and representative-load tests.

07. Proposed architecture

┌────────────────────┐ Internet ──► CloudFront ──┤ Static assets: S3 │ │ └────────────────────┘ │ Dynamic routes ▼ API Gateway HTTP API │ ▼ AWS Lambda + Bref Laravel runtime │ │ │ ▼ ▼ ▼ PlanetScale Upstash S3 / SQS Vitess Redis files / jobs PS-20 ↔ PS-160 Prefer Lambda outside the VPC: public TLS to PlanetScale and Upstash; managed AWS APIs for S3/SQS/SES.

Scale per request

No continuously running Nginx or PHP-FPM tasks during idle periods.

Separate assets

CloudFront and S3 absorb static-file traffic without invoking PHP.

Separate state

PlanetScale stores durable business records; Upstash stores temporary sessions and cache.

PS-160 upgrade premium = ($349 − $59) ÷ 720 × 8 hours ≈ $3.22

Resize one to two hours before an exam. Downsize only after answer submission, grading, and queue activity return to normal.

09. Bref / Lambda feasibility

Conclusion: feasible with application changes. Bref runs complete Laravel HTTP applications through its PHP-FPM runtime on Lambda.

Compatible characteristics

  • Conventional Laravel HTTP application
  • Existing S3 and AWS SDK usage
  • No persistent ECS volume
  • Low average, bursty traffic
  • No application websocket server identified
  • PDF and Excel can run if they fit Lambda limits

Required changes

  1. Upgrade unsupported PHP 8.0 and Laravel 8
  2. Add Bref and Laravel Bridge
  3. Move static assets to S3/CloudFront
  4. Move sessions/cache to Upstash
  5. Use /tmp only for temporary files
  6. Use direct S3 uploads for large files
  7. Move long work to SQS-triggered Lambda
  8. Apply reserved concurrency

Key constraints

ConstraintImplicationResponse
Cold starts, typically a small fraction of trafficAdded latency, especially for large legacy appsOptimize package; provision concurrency during exams
15-minute invocation maximumLong imports/reports cannot remain synchronousSplit work or retain a dedicated job path
Read-only package filesystemFile sessions/cache and durable uploads failUse Upstash, S3, and /tmp
HTTP upload/payload limitsLarge Excel/image uploads may failPresigned direct-to-S3 upload
Fast concurrency growthCan overload PS-20 or RedisReserved concurrency and load-tested limits

10. Upstash Redis design

Upstash matches the serverless operating model and avoids retaining an always-on ElastiCache node or placing Lambda in a VPC solely for Redis.

Production sessions

  • Dedicated Upstash database
  • TTL longer than the full exam window
  • No cache flush coupling
  • Monitor p95 latency and errors

Application cache

  • Separate database
  • Safe to flush independently
  • Rate limits and short-lived locks
  • Explicit TTLs and budget alerts

14. Migration plan

Measurement

Record logical DB size, request latency, file upload sizes, long-running jobs, Redis command estimate, and candidate counts.

Application modernization

Upgrade PHP/Laravel; create a database-free health endpoint; move sessions/cache; externalize static assets.

Bref and Upstash prototype

Deploy staging Lambda outside the VPC; validate login, CSRF, session expiry, files, PDF, Excel, admin flows, and logs.

PlanetScale prototype

Validate schema compatibility, transactions, read-after-write behavior, migration, restore, and resize procedures.

Representative load test

Sustain 49 dynamic req/s, test 100+ req/s bursts, submit answers concurrently, and run a controlled 510-request burst.

Parallel production validation

Retain ECS/Aurora rollback; route limited traffic; compare correctness, latency, and cost.

Production migration

Cut over outside exam windows. Observe one complete exam event before optimizing sizes or decommissioning the old stack.

15. Success criteria

Correctness

  • No lost or duplicated answers
  • Correct session and CSRF behavior
  • PDF, Excel, upload, and admin flows pass
  • Rollback tested

Performance

  • Agreed p95/p99 latency
  • No DB connection saturation
  • Exam load passes with headroom
  • Resize completes before traffic

Economics

  • Application hosting below $25/month normally
  • PS-20 normal baseline
  • At least 60% combined reduction
  • No unexpected NAT/egress cost

16. Recommendation and decision request

Approve a time-boxed, non-production prototype for Laravel on Bref, PlanetScale Vitess, and Upstash Redis. Proceed to migration planning only if the prototype meets correctness, representative-load, latency, operability, and cost criteria.
